CS382 Final Project

Book Search Assistant

A Retrieval-Augmented Generation system that answers questions about 20 popular self-improvement books — grounded in a purpose-written corpus, with visible citations, similarity scores, and a refusal path when the sources don't hold an answer.

  • Python
  • Streamlit
  • sentence-transformers
  • Google Gemini
  • RAG
Watch Demo Video View Slides Source on GitHub

The problem

Self-improvement books repeat and contradict each other. A reader with a real question — "how do I stop procrastinating?" — doesn't want a keyword match; they want an answer synthesised across books, with a pointer back to which book said what so they can verify it and read further.

Keyword search fails this outright. The query "how can I stop caring about other people's opinions?" shares almost no vocabulary with the passage that answers it in The Courage to Be Disliked. The goal was a system that retrieves by meaning, generates an answer grounded only in what it retrieved, and says so plainly when nothing relevant exists.

Architecture

Four independent modules with stable interfaces. Each layer was upgraded from the TF-IDF starter without touching the others — the interface boundaries were the point, not an accident.

  1. 1

    Corpus — data/books/

    25 documents: 20 original book study notes (~900 words each) plus 5 thematic guides that compare books across a theme, with catalog.json metadata.

  2. 2

    Ingest — rag/ingest.py

    Sentence-aware chunking at a ~180-word budget with 2-sentence overlap, producing 119 chunk records. No sentence is ever split across a boundary.

  3. 3

    Embed & retrieve — rag/embed_store.py

    all-MiniLM-L6-v2 embeddings into an L2-normalised matrix, disk-cached by corpus hash, queried by cosine top-k. Falls back to TF-IDF if the model isn't installed.

  4. 4

    Generate — rag/generate.py

    A grounded prompt to Gemini that requires citations, with an extractive fallback. Refuses outright when the retrieved sources don't answer the question.

  5. 5

    Interface — app.py

    Streamlit UI: query form, answer panel, expandable sources with similarity scores, top-k slider, answer-mode toggle, and latency display.

Design decisions

Original study notes, not book text

The 20 books are copyrighted, so the corpus is original study-note documents written for this project — core thesis, key frameworks, practices, cross-references. The 5 thematic guides were added deliberately, and the evaluation confirmed they earn their place: comparison and recommendation queries retrieve them first.

Sentence-aware chunking over fixed windows

The starter split on fixed word counts, cutting sentences in half. A ~180-word budget that respects sentence boundaries, with 2-sentence overlap, keeps boundary-spanning ideas retrievable without fragmenting meaning.

Embeddings over TF-IDF

Retrieval by meaning rather than word overlap. all-MiniLM-L6-v2 runs locally and free, so retrieval carries no API dependency — only generation does.

In-memory cosine search, not a vector database

At 119 chunks a normalised matrix multiply takes ~100 ms; FAISS or Chroma would add operational complexity for no gain at this scale. The VectorStore.build/query interface is deliberately DB-shaped so one could be swapped in for a larger corpus.

A fallback chain, so the demo cannot break

Gemini with retry and fallback models on transient 503s, degrading to extractive passages. A missing key, a down API, or a provider load spike cannot take the live demo down.

Graceful failure by relevance floor

If no chunk scores at least 0.20 cosine, the app reports that it found nothing relevant and never calls the LLM. Off-topic questions are structurally incapable of producing a hallucinated answer — the guard sits before generation, not after.

What worked

  • Semantic retrieval genuinely beat the baseline. Query 2 names no book at all, yet the embedding model maps "stop caring about other people's opinions" onto the right passages in three different books. Under TF-IDF that query mostly matches stop-words.
  • The thematic guides earned their place. On comparison and recommendation queries, a purpose-written cross-book guide outranks the individual books and hands the LLM a ready-made comparison to ground on.
  • Grounding held. Every generated answer cited only books present in the retrieved context, and the off-topic query never reached the LLM at all.

What didn't — and what the evaluation changed

  • The relevance floor was too strict at 0.30. Query 4 ("the 40% rule", scoring 0.232) was wrongly refused: short named-concept queries produce low cosine scores because the query carries almost no context. I tuned the floor to 0.20, which keeps a margin above the off-topic score of 0.166 — though with only one off-topic probe, that margin is thin.
  • Answers were truncating mid-sentence. The newer Gemini models spend part of the token budget on internal reasoning, so a 1,000-token cap cut answers off — query 6 originally ended "…boredom [Deep". Raised to 3,000.
  • Latency is dominated by generation at ~10–18 s per answer, plus a ~7 s one-time model load. Disk-caching the embedding matrix removed the retrieval cost; only generation remains.

What I learned

Evaluation is a design tool, not a report card

I expected to run the eval at the end and write down a number. Instead it drove two concrete fixes — the relevance floor and the token budget — that I would never have found by manually trying queries I already knew the answers to. The off-topic probe in particular only earns its keep because it can fail.

Refusing well is a feature

The instinct is to always return something. Putting the relevance floor before the LLM call made refusal structural rather than a matter of prompt wording — the model can't hallucinate about chocolate cake if it's never asked.

Module boundaries paid for themselves

Swapping TF-IDF for embeddings touched exactly one file because ingest, embed_store, and generate only talk through narrow interfaces. That decision cost a little upfront and saved the rewrite.

Match the tool to the scale

Reaching for a vector database at 119 chunks would have been resume-driven engineering. Knowing when not to add infrastructure turned out to be as much of a design decision as any component I did add.

Limitations & next steps

  • Answers reflect the study notes' coverage of each book, not the full text — a question about an obscure chapter detail may correctly return "not enough information".
  • The 0.20 relevance floor was tuned against a single off-topic probe. A larger negative test set would tighten it, and similarity scores are not calibrated probabilities, so the floor would need re-tuning for a different corpus.
  • Single-turn and English-only: no conversation memory.
  • Streaming the generated response would cut perceived latency substantially, since the wait is almost entirely generation time.
